# Интеграция фармацевтического флоу (ЛС и МИ) в портал

> Статус: **план**. Экраны самой подачи заявки и АРМ эксперта пока живут в Figma
> и в этот проект не перенесены.

## Задача

Соединить два продукта:

1. **Единый портал МЗ РК** (этот проект) — витрина: разделы, каталог услуг,
   паспорта услуг, авторизация.
2. **Система подачи заявок на лекарственные средства (ЛС) и медицинские изделия (МИ)**
   (спроектирована в Figma) — заявитель подаёт заявку, эксперт в АРМ проводит модерацию,
   отказывает или возвращает на доработку.

Целевой путь пользователя:

```
Портал → роль «Бизнесу» → таб «Фармацевтика» → выбор услуги
      → Паспорт услуги → кнопка «Получить услугу»
           ├─ авторизован  → форма подачи заявки
           └─ не авторизован → Вход (ИИН/ЭЦП, профиль «Бизнес») → возврат → форма подачи
      → подача → статусы заявки в кабинете заявителя
                               ↕
                        АРМ эксперта (модерация)
```

### Гейт «Получить услугу» (реализован)

```
Паспорт услуги (портал) → «Получить услугу»
  ├─ не вошёл как бизнес → Вход?profile=business&return=Паспорт услуги?start=1#price-ls
  │     вход по ЭЦП (выбран по умолчанию), профиль «Бизнес» первым → возврат в паспорт → гейт продолжает сам
  ├─ онбординг не пройден (mp-biz-step 1|2) → окно «Подготовьте организацию к подаче»
  │     шаги со статусами, кнопка на нужный раздел; услуга запоминается (mp-pending-service)
  │     Договора: «Сохранить договор» (НЦЭЛС) или принятие оферты → шаг 2, тост «Создать заявку на платеж»
  │     Платежи: создание заявки на платеж → шаг 3, тост «Продолжить подачу»
  │     Главная кабинета: баннер «Организация готова к подаче — Продолжить подачу»
  └─ готово → лоадер «Открываем форму заявки…» → Заявка на регистрацию цены#ls|#mi
```
Если заявка уже подана, паспорт показывает её статус и «Мои заявки». Вошедшей организации шапка портала показывает «Кабинет бизнеса» вместо «Войти».
| Вход с выбором профиля | `Вход.dc.html` | **есть**. Профиль «Бизнес» ведёт в `Кабинет бизнеса.dc.html`, поддерживает `?return=<страница>`. |
| Кабинет заявителя (юрлицо) | `Кабинет бизнеса.dc.html`, `Мои процессы.dc.html`, `Процесс.dc.html`, `Договора.dc.html`, `Платежи.dc.html`, `Услуги.dc.html`, `BusinessNav.dc.html` | **есть**: главная с онбордингом, «Мои процессы», страница процесса, Договора (iframe НЦЭЛС + оферта ННЦРЗ), Платежи (iframe), реестр Услуг, заявление КНФ, Центр уведомлений. |
| Подача заявки на регистрацию цены ЛС / МИ | `Паспорт регистрации цены.dc.html`, `Заявка на регистрацию цены.dc.html` | **есть, демо**: паспорт → мастер из 5 шагов (статично) → ЭЦП → ожидание проверки → итог. Один путь на ЛС («Иностранного производителя») и один на МИ («ввозимого»). |

## Что предстоит сделать

### Этап 1. Достроить портальную часть (можно делать уже сейчас)

1. **Расширить `Паспорт услуги.dc.html`**
   - Добавить в `DB` услуги фармацевтики:
     `price-ls` (регистрация цены на ЛС), `price-mi` (регистрация цены на МИ),
     `license-pharma` (лицензия на фармдеятельность).
   - Ввести флаг вида `internal: true` — для таких услуг кнопка называется
     **«Получить услугу»** и ведёт внутрь портала, а не на `elicense.kz`,
     и информационный баннер про elicense не показывается.
   - Получатель услуги для них — «Юридические лица», а не «Физические лица».

2. **Развести ссылки на главной**: пункты «Регистрация цены на ЛС / МИ» и
   «Лицензия на фармацевтическую деятельность» → `Паспорт услуги.dc.html#price-ls` и т.д.,
   вместо `Каталог услуг.dc.html`.

3. **Гейт авторизации**. Кнопка «Получить услугу»:
   - есть `localStorage['mp-profile'] === 'business'` → сразу на форму заявки;
   - иначе → `Вход.dc.html?return=<страница заявки>`, после выбора профиля «Бизнес»
     возврат по `return`.
   Для этого в `Вход.dc.html` научить шаг `role` читать `return` из query
   и подставлять его в `href` профиля.

4. **Кабинет заявителя (юрлицо)** — новая страница `Кабинет бизнеса.dc.html`
   по образцу `Личный кабинет.dc.html`:
   разделы «Мои заявления» (реестр со статусами), «Мои разрешительные документы»,
   «Уведомления», «Профиль организации».
   Шапка подключается как `<dc-import name="Header" variant="account">`.

### Этап 2. Перенести флоу подачи из Figma

По одному экрану, каждый — отдельный `.dc.html`. Ориентировочно:

- `Заявка ЛС — шаг 1 … N.dc.html` (или одна страница с мастером внутри — решим,
  когда увидим фигму: если шагов ≤ 6 и они линейные, лучше одна страница с `state.step`).
- Экран подтверждения / подписания ЭЦП.
- Экран статуса заявки (таймлайн рассмотрения, замечания эксперта, возврат на доработку).

Перед переносом нужен **стыковочный словарь**: как называются статусы заявки в Figma
и как они лягут на `StatusBadge` дизайн-системы
(например: Черновик / На рассмотрении / На доработке / Отказано / Зарегистрировано).

### Этап 3. АРМ эксперта

Отдельный кабинет (`АРМ эксперта.dc.html` + подразделы):
реестр заявок с фильтрами, карточка заявки, сравнение версий после доработки,
решение (одобрить / отказать / вернуть), журнал действий.

Раскладка — как в `Кабинет врача.dc.html` (левое меню + рабочая область);
референс раскладки также есть в `design-system/src/ui_kits/medical-portal/`.

   с доверенностью?

4. Возврат на доработку — заявитель правит ту же заявку (версионирование)
   или подаёт новую со ссылкой на предыдущую?
5. У эксперта одна роль или их несколько (регистратор / эксперт / руководитель,
   с согласованием решения)?
6. Оплата: услуга бесплатная или есть госпошлина? Если есть — нужен экран оплаты.
7. Портал МЗ — это единая точка входа вместо elicense.kz по этим услугам,
   или они сосуществуют?
