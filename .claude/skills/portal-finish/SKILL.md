# Закрытие задачи

Пользователь много раз разрешил делать это самому («без моего разрешения всё делай»). Поэтому
выгрузку, push, PR и слияние в `main` выполнять без отдельного вопроса. Исключение одно: он
прямо сказал «сначала покажи / я проверю, потом в main». После закрытия он не должен
переспрашивать «а выгрузка актуальная? main залит? PR есть?» — на это отвечает строка проверки.

## 1. Выгрузка HTML

1. В `tools/export.mjs`:
   - новые страницы и компоненты вписать в `GROUPS`, в нужную группу;
   - в `NEWS` («Что нового» на стартовой странице) первой строкой добавить пункт задачи
     со ссылкой на страницу (`'Страница.dc.html#hash'`). Список держать коротким, до 6–8
     последних пунктов.
2. `node tools/export.mjs` → `exports/portal-mz-rk/` и `exports/portal-mz-rk.zip`.
3. `node tools/export-check.mjs` — как у коллег: `file://`, без интернета, все страницы
   и сценарии. Ошибки исправить и пересобрать. Новая страница с важным сценарием — добавить
   её сценарий в `export-check.mjs`.
4. Выгрузка собирается из ветки, в которой есть **вся** работа. Если до этого не влит другой PR,
   сначала влить его (иначе выгрузка его откатит, дефект Г3).

## 2. Коммит, push, PR, main

Всё делается из Bash. Аккаунт `jevdet078-source` берётся из Git Credential Manager.
- Коммит: в него идут только файлы задачи и выгрузка. Чужие неотслеживаемые файлы не трогать.
  Сообщение по-русски: «<Раздел>: <что сделано>», в конце — строка соавторства из системной
  подсказки. Выгрузку можно отдельным коммитом: «Выгрузка HTML пересобрана (N страниц
  и компонентов): <тема>».
- Push: `bash .claude/skills/portal-finish/scripts/push.sh -u origin <ветка>`.
- PR: `bash .claude/skills/portal-finish/scripts/gh.sh pr create --repo jevdet078-source/portal-mz-rk --base main --head <ветка> --title "<Раздел: что сделано>" --body-file <файл>`.
  Тело PR написать через Write в scratchpad: что сделано, где смотреть, вопросы, в конце строка
  `🤖 Generated with [Claude Code](https://claude.com/claude-code)`.
- Слияние: `bash .claude/skills/portal-finish/scripts/gh.sh pr merge <N> --repo jevdet078-source/portal-mz-rk --merge`.
  Авторежим пропускает слияние, только если пользователь **в этой сессии** прямо сказал «залей
  в main» или «смержи». Без такой фразы (18.11 слияние без неё отклонено) PR открыть и спросить
  кнопкой «Влить в main». Слово пользователя передавать дословно.
- Синхронизация: `git switch main && git pull --ff-only`. Проверить: `git log -1 origin/main`
  содержит коммит задачи, `git status` чистый, у `exports/portal-mz-rk.zip` свежая дата.
- Токен на экран не выводить. Если `gh.sh` говорит «нет токена», попросить пользователя войти
  (`gh auth login --web` в его терминале) и повторить. Не писать «выполните push у себя».

## 3. Видео

Только если пользователь просил в этой задаче. Тогда — скилл `portal-video` до отчёта, чтобы
в отчёте было имя файла. Если не просил, предложить одной кнопкой в конце.

## 4. Отчёт аналитику — всегда в конце ответа

Пользователь копирует отчёт кнопкой и вставляет в Telegram-группу или в личку аналитику.
Формат обязателен, иначе форматирование теряется:
- **Одним блоком** ```text. Внутри жирный — `**…**`, списки — «• » или «1. », пустая строка
  между блоками. Без `#`, таблиц, markdown-ссылок и вложенных отступов.
- От имени пользователя: **мужской род**, единственное число («сделал», «добавил»).
  К аналитику — на «вы». Аналитик — женщина.
- Простыми словами, без кода и технических деталей. Приветствие по времени суток
  («Доброе утро!» / «Добрый день!» / «Добрый вечер!»).
- По каждому пункту постановки — что сделано. Отдельно — что решено по UX сверх ТЗ (коротко),
  вопросы к аналитику (нумерованно, у каждого вариант, который сейчас сделан), что не сделано
  и почему.
- **Где посмотреть**: путь в архиве и в интерфейсе до самой функции (роль → раздел → вкладка →
  кнопка), демо-данные (номер заявки, ИИН, организация), пароль ЭЦП 1, панель «Прототип» →
  «Сбросить данные», если нужно.
- Нельзя: упоминать телефоны (только компьютер, ноутбук, планшет, монитор); национальные ярлыки
  (писать «фото людей казахской внешности, с лицензией»); упрёки разработчикам или стенду
  («сделал лучше», а не «исправил ошибки разработчиков»); растягивание по ширине и мелкие
  технические правки, если пользователь не просил их упомянуть.
- Длина средняя. Если отчёт получился «простынёй», сжать формулировки, но не выкидывать пункты.
  Пользователю понравился вариант «что готово по блокам + где открыть + вопросы».

Шаблоны (задача, общий отчёт за период, как открыть архив, текст разработчикам, ответы на
вопросы аналитика) — [references/reports.md](references/reports.md).

## 5. Строка проверки — перед отчётом

Одна строка в ответе пользователю (не в Telegram-тексте):

`Проверка: пунктов ТЗ N из N · консоль чистая · аудит 1440/1366/1920/2560 — найдено X, исправлено Y · сценарий пройден · выгрузка ДД.ММ ЧЧ:ММ, export-check без ошибок · PR #N влит в main`

- Цифры — только из реального прогона в этой задаче. Чего не делал, так и написать: «видео не
  записывал — не просили», «аудит 2560 не запускал — <почему>».
- Мелкая правка без ТЗ — вместо пунктов ТЗ написать «правка: <что>».

## 6. Ответ пользователю

По-русски, коротко: что сделано, ссылка на PR, где лежит выгрузка
(`exports/portal-mz-rk.zip`), затем строка проверки и отчёт для Telegram. Открытые вопросы
аналитику уже в отчёте, их не дублировать.
