# Постановка аналитика → готовый результат

Пользователь — UX/UI-дизайнер портала. Длинные промпты он больше не пишет. Всё, что он раньше
повторял в каждой постановке, теперь лежит здесь и в скилле `portal-ux`. Короткий промпт и файл
означают **полный стандарт без скидок**: высший уровень UX/UI, ничего не пропустить, ничего не
добавить от себя, никакого визуального шума, финальная проверка с исправлением ошибок.

Порядок работы утвердил сам пользователь: прочитать → подумать и сделать ресерч → реализовать →
проверить и исправить → закрыть. К реализации сразу не приступать.

## Шаг 0. Старт

1. **Первым действием** загрузить скилл **`portal-ux`** инструментом Skill. Не полагаться на память,
   даже если он уже встречался в сессии. После сжатия контекста загрузить заново.
2. Git (Bash, из корня репо):
   - `git status`: есть чужие незакоммиченные изменения — сказать о них, ничего не откатывать;
   - `git fetch origin` и `git log --oneline -5 origin/main`;
   - открытые PR: `bash .claude/skills/portal-finish/scripts/gh.sh pr list --repo jevdet078-source/portal-mz-rk --state open`
     (токен `jevdet078-source` скрипт берёт сам и не показывает). Если есть открытый PR,
     сказать пользователю и предложить сначала его влить. Иначе выгрузка из новой ветки откатит
     несмёрженную работу: так однажды потеряли страницу госуслуг;
   - новая ветка от свежего `main`: `git switch -c feature/<кратко-латиницей> origin/main`.
     Доработка по замечаниям к ещё не влитой ветке — работать в той ветке.
3. **Строка старта** — первая строка ответа пользователю, после загрузки скилла и чтения ТЗ:
   `Скиллы: portal-task, portal-ux · тип: <новый раздел / замечания / …> · роль: <гражданин / бизнес / медперсонал / АРМ …> · пунктов ТЗ: N`

## Шаг 1. Прочитать всё, что приложено

Читать целиком, до последней строки и картинки. Половина замечаний аналитика живёт на скриншотах:
красным зачёркнуто то, что надо убрать, обведено то, что надо поменять.

| Что | Как читать |
|---|---|
| `.docx` | `node .claude/skills/portal-task/scripts/docx-extract.js "<файл>" "<scratchpad>/tz/<имя>"` → прочитать `tz.md` полностью и **открыть каждую картинку** из `media/` (Read). Метка `[РИС N: …]` показывает, к какому пункту относится рисунок |
| `.doc` из Confluence (это MHTML) | `node .claude/skills/portal-task/scripts/doc-extract.mjs "<файл>" "<scratchpad>/tz/<имя>"` → такой же `tz.md` + `media/` |
| `.pdf` | Read с `pages` (по 20 страниц) |
| `.bpmn` | Read: роли (lanes), задачи, развилки (gateway) и тексты условий. Это порядок процесса и статусы |
| `.xml` / `.xsd` / `.txt` запросов сервиса | набор полей, обязательность и коды ошибок. Поля в UI берутся **отсюда**, не придумываются |
| `.zip` с прототипом аналитика (HTML, Google Stitch) | распаковать в **новую пустую папку** scratchpad. Снимки страниц: `node .claude/skills/portal-task/scripts/ref-shots.mjs "<папка>" "<папка>/shots"` → посмотреть PNG. Код референса не запускать иначе и не копировать |
| Ссылка Figma | Figma MCP (`get_design_context` / `get_screenshot` по node-id). Карта файла «Единого окна» — в памяти `edinoe-okno-figma` |
| Тестовый стенд `portal.isapp` и другие сайты | встроенный браузер, только смотреть, ничего не вводить. Не открывается — попросить скриншоты |
| Текст аналитика из Telegram, ответы на прошлые вопросы | тоже часть постановки, с тем же весом |

## Шаг 2. Чек-лист пунктов

Выписать **все** требования нумерованным списком: «п. N → что меняется → где (страница / окно /
состояние)». Ничего не объединять по смыслу и не опускать мелочи: подпись, порядок полей,
умолчание, текст ошибки, статус. Тексты ошибок, статусов и названия полей брать **дословно**.

- Средняя и большая задача: сохранить в `docs/tz/<ГГГГ-ММ-ДД>-<раздел>.md` (источники, выжимка,
  чек-лист со статусами, решения по UX, вопросы). Следующие замечания по той же теме начинаются
  с этого файла.
- Расхождения между источниками (Word и Confluence, BPMN и UC, постановка и стенд) не решать
  молча. Взять самый свежий и полный вариант, отметить в файле ТЗ и в `docs/06-backlog.md`,
  вынести вопросом в отчёт.

## Шаг 3. Тип задачи, роль, место

| Тип | Признак | Как действовать |
|---|---|---|
| **Новый раздел / модуль** | «реализовать», «добавить раздел», страницы ещё нет | Найти ближайший по типу готовый экран (`portal-ux/references/patterns.md`) и повторить каркас: шапка, навигация, реестр, паспорт, мастер, карточка. Новая страница — новый `.dc.html` в плоской `project/`; общие куски — компонентом |
| **Замечания после тестирования** | Word со скриншотами, «аналитик протестировала» | Исправить ровно отмеченное. Тот же дефект найти и исправить во всех экранах раздела. Остальное не перестраивать и **ничего не ломать** |
| **Перенос из Figma «Единого окна»** | ссылки на `cMe8P7iJNaTBgG04okquEG` | Экраны «Единого окна» — **1:1**, менять можно только оболочку портала (шапка, навигация, вход, переходы). Мастер — первый и последний шаг |
| **Информация из Figma или с сайта → наш шаблон** | «возьми информацию, сделай по нашему шаблону» | Данные — из источника, вёрстка — по готовому шаблону портала (паспорт услуги, реестр), «чтобы не было разнобоя» |
| **Привести в соответствие со стендом** | `portal.isapp`, «у нас на портале так выглядит» | Состав и смысл как на стенде, ошибки UX/UI стенда (их тоже генерировали AI) у себя исправить. Отчёт: «сделал лучше», без упрёков разработчикам |
| **Главная страница** | «главная», «варианты главной», руководство, вице-министр | `portal-ux/references/home.md`. Какие варианты трогать, решает пользователь (обычно последние; итоговый — J). Существующие варианты не менять без просьбы |
| **Мелкая правка** | «убери», «перенеси», «добавь слово» | Точечно. Проверить, где ещё встречается тот же элемент |
| **Презентация / слайд** | `.pptx`, «слайд для министра» | Это не здесь, а в скилле `portal-deck` |

**Роль и кабинет** определить до реализации: Гражданам / Бизнесу / Медперсоналу, ЛК гражданина,
кабинет бизнеса (заявитель / администратор), кабинет врача, АРМ (ННЦРЗ, ФК, НЦЭЛС), первый
руководитель медорганизации. Постановка про ЭПЗ без явной роли относится к кабинету врача.
Просмотр ЭПЗ общий (`EpzView`), поэтому проверять оба режима. Роль неясна и решение от неё
зависит — спросить.

**Объём.** Средняя задача (один раздел, 1–5 экранов) делается за одну сессию без дробления.
Огромная (несколько UC, много ролей) — предложить 2–3 этапа с планом в `docs/tz/…`, по образцу
`docs/10-alo-plan.md`; запускать только после согласия.

## Шаг 4. Подумать и сделать ресерч (до кода)

Коротко и для себя. Пользователю показать только итог одной-двумя строками.
1. Главная задача экрана одним предложением, главный пользователь и его частое действие.
2. Как это решают лучшие: eGov.kz, Госуслуги, gov.uk / NHS App, MyChart (пациент), Kaspi / Halyk
   (оплата, QR), банки (витрины, баннеры), Linear / Stripe Dashboard (реестры, фильтры). Задача
   с конкретикой (платёж, загрузка документов, согласие, опросник) — посмотреть 2–3 живых примера
   встроенным браузером.
3. 3–5 решений по раскладке и взаимодействию: что сверху, что в таблице, что в карточке, где
   основное действие, какие состояния. Сверить с правилами `portal-ux`.

## Шаг 5. Вопросы — только настоящие

Спрашивать, только если пункты ТЗ противоречат друг другу или решение меняет процесс: роли,
статусы, что сохраняется, кто видит. Вопросы — коротким нумерованным списком, у каждого вариант по
умолчанию. Если вопросы не блокируют работу, делать с вариантом по умолчанию, а вопросы вынести
в отчёт аналитику. Всё, что решается по UX, решать самому.

## Шаг 6. Реализация

По `portal-ux`: правила, «не AI-слоп», паттерны, код `.dc.html`. Перед каждым новым элементом
поискать готовый в `project/`. Демо-данные для каждого состояния. Переключение ответов сервиса —
панель «Прототип», как у соседних страниц. Коммитить осмысленными кусками в ветку задачи.

## Шаг 7. Финальная проверка — обязательно

Протокол `portal-ux/references/final-check.md` целиком: сверка с чек-листом ТЗ, консоль,
автоаудит на 1440 / 1366 / 1920 / 2560 (и 768 / 375 на переполнение), взгляд глазами придирчивого
аналитика, основной сценарий от начала до конца. Найденное исправить и проверить повторно.
У средней и большой задачи после этого — независимый взгляд субагента (раздел 6 протокола).

## Шаг 8. Закрытие

1. Закоммитить в ветку задачи.
2. Строка проверки (формат — `portal-finish`, раздел 5).
3. По умолчанию сразу выполнить скилл **`portal-finish`**: выгрузка HTML + проверка выгрузки → push →
   PR → влить в `main` → отчёт аналитику для Telegram. Пользователь много раз прямо разрешил
   делать это самому. Слияние проходит, только если в сессии прозвучало «залей в main»; иначе PR
   открыт и вопрос кнопкой «Влить в main».
   **Исключение:** в сообщении сказано «сначала покажи / сначала видео / я проверю, потом в main».
   Тогда сделать только выгрузку (и видео, если просили), остановиться и спросить кнопкой
   «Залить в main и отчёт».
4. Видео записывать, только если пользователь попросил в этой задаче (скилл `portal-video`).
   Иначе предложить его одной кнопкой в конце.

Пользователю не нужно отдельно писать «сделай отчёт», «обнови выгрузку» или «проверь, что main
актуален»: всё это входит в задачу и подтверждается строкой проверки.
